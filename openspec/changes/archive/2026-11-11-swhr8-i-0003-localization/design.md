# Legacy implementation notes: localization

- Locale list and default live in web.xml init-params/env-entries (`locales`, `default_locale`) and in `conf/petstore.properties` (`catalog.locales`, `catalog.defaultLocale`); the properties file header says web.xml holds the live values. The deployed template servlet lists `locales=en_US` only, so other locales currently fall back to the default screens.
- Per-locale screen definition files (en_US, ja_JP, zh_CN) and per-locale page directories exist under the petstore app.
- `changelocale.do` is mapped to ChangeLocaleHTMLAction (stores the Locale in the session attribute under WebKeys.LOCALE and emits a ChangeLocaleEvent). `changelocale.jsp` / `changelocalesuccess.jsp` are WAF demo pages; reachability from the storefront was not established.
- `MainServlet.doProcess` sets the default session locale; `TemplateServlet` resolves request parameter, then session, then default.
- `I18nUtil.getLocaleFromString` (also copied as the order-processing `LocaleUtil` and in CatalogHelper) never assigns variantIndex, so variants are lost and `en_US_x` yields a null country; a string with no underscore yields null. Catalog DAO then dereferences the locale (NPE).
- `I18nUtil.convertJISEncoding` swallows unsupported-encoding errors and returns null; `parseKeywords` returns null on error. No caller seen in the module.
- `EncodingFilter` field default "ASCII" is always overwritten in init() by the init-param (null when absent), so the default is dead. Deployed config supplies UTF-8, mapped to `/*`. Record LOC-BR-0002 (encoding filter pass) is described here rather than as a requirement because its key collides with the WAF record of the same key.
- `CustomerEJBAction.updateCustomer` sets a literal "locale" attribute key where other code uses PetstoreKeys.LOCALE; equivalence unverified.
- Catalog `*_details` tables are keyed (id, locale), locale varchar2(10); the value set is not constrained in DDL.
- Order e-mail stylesheet chosen by locale in MailContentXDE via LocaleUtil.
- Session timeout 30 minutes is a bare web.xml literal.
- Screen record LOC-REQ-0005 (pass a) and LOC-REQ-0008 (pass b) describe the same locale selection page.

# Sprint SWHR8-S-0002 planning notes

Added by planning (SWHR8-T-0007). The legacy notes above are kept unchanged. Owning ticket: **SWHR8-T-0008** (one FEATURE for the whole change). Plan: `artifacts/SWHR8-S-0002/SWHR8-T-0008/PLAN.md`.

## Codebase findings

- **Stack**: Vite + React 19 SPA with a Nitro 3 / H3 2 server in one process (`vite.config.ts`, `nitro({ serverDir: "./" })`). Pages are file-based under `src/pages/`, API handlers under `routes/api/`, request middleware under `middleware/`. Everything runs under Bun.
- **What exists for this capability**: a placeholder only. `routes/api/locales.ts` returns `[{ code: "en_US" }]` and says "The Localization capability replaces this source". `src/pages/localization/index.tsx` lists those codes through `useLoad` with the shared empty/error/loading frames. `src/constants/primary-areas.ts` has one area, Language, at `/localization`. There is no session, no locale state, no `<html lang>` handling, and no translated string anywhere.
- **Shell**: `src/pages/_layout.tsx` is the only header/nav/footer. Its strings ("Home", "Explore", footer tagline, menu button labels) are hard-coded English.
- **Database**: `db/schema.ts` has only the demo `users` table. No catalog table exists yet. Catalog browsing (SWHR8-I-0004) builds the category/product/item tables.
- **Locked acceptance suite** (`tests/acceptance/localization/`, read-only for the implementer) fixes the module boundaries:
  - `localization.test.ts` imports `server/localization/{details,catalog-text,locale,sessions,screens,mail}.ts` from the repo root, with the exact factory names and signatures in its header comment. `server/` does not exist yet, and `tsconfig.node.json` does not include it.
  - `localization.spec.ts` fixes the browser contract: Language page at `/locale` with a `<select>` labelled "Language" (options exactly `en_US, de_DE, ja_JP, zh_CN`, in that order), a "Change language" button, `[data-testid="session-locale"]` on success, `role="alert"` containing "unable to change" on failure; `GET /api/session -> { locale }`; the session must be cookie-based because the spec reads it with `page.request`, which shares the page's cookies.
- **Locked site-shell suite** (`tests/acceptance/site-shell/state-frames.test.tsx`, cases SWHR8-C-0139/0140) renders `@/pages/localization` with a stubbed `fetch`: an empty array must show the empty frame and a rejected fetch must show the error frame with a working retry. The Language page must keep that loading behaviour.
- **Runtime capability**: Bun 1.4.4's `TextDecoder` decodes `shift_jis` correctly, but `iso-2022-jp` (JIS) and `euc-jp` produce mojibake. Checked in the agent container.
- **Customer account** (SWHR8-I-0005) acceptance tests also use `GET /api/session` (adding `signedOn`, `userName`, `cartCount`) and expect sign-off to keep the locale. The session therefore has to be one shared mechanism.

## Decisions

- **L1 Module layout follows the locked tests.** Pure server modules live in `server/localization/`: `locale.ts` (config, code parsing, notification locale, currency/number formatting, UTF-8 form reading, Japanese decoding), `sessions.ts`, `screens.ts`, `details.ts`, `catalog-text.ts`, `mail.ts`. Each takes its clock, config and data as arguments so it is testable without a server. `tsconfig.node.json` gains `server`. Their own unit tests run in the vitest `server` project (node environment), which is extended to include `server/**/*.test.ts`.
- **L2 Locale codes.** A valid code is `language_COUNTRY` (2–3 letters, underscore, 2 letters), normalised to `ll_CC`, or the literal `default`, which means the configured default. Anything else, including a missing value and legacy three-part `en_US_x` codes, is unparseable. Change-locale rejects with an error whose message contains "Unable to change the language". Notification derivation returns `null`. Any parseable code is accepted as a session locale, not only the three supported ones. That is how `de_DE` is selectable and then falls back to en_US screens.
- **L3 Configuration.** `loadLocaleConfig({ locales, default_locale })` parses the comma list. The server reads it from `LOCALES` / `DEFAULT_LOCALE` env vars, defaulting to `en_US,ja_JP,zh_CN` and `en_US`. `GET /api/locales` returns the configured codes. The legacy deployed `locales=en_US` value is not reproduced (see discrepancy S2).
- **L4 Session.** One in-memory session store (`createLocaleSessions`) with a 30-minute idle timeout, addressed by an HTTP-only, `SameSite=Lax` cookie. `middleware/locale.ts` resolves or creates the session on every request (renewing an expired one, which yields the default locale), sets the default locale when absent, and exposes `event.context.sessionId` and `event.context.locale`. A `?locale=` query parameter overrides the locale for that one request only. Endpoints: `GET /api/session -> { locale }`, `POST /api/locale { locale } -> 200 { locale }`, or `400` with message "Unable to change the language" when the session is unchanged. Later capabilities attach their state to this same session id and extend `/api/session` additively. They never mint a second session.
- **L5 Screens.** Screen definitions are per-locale string dictionaries, `src/i18n/screens/{en_US,ja_JP,zh_CN}.ts`. No `de_DE` dictionary exists, on purpose. `createScreenResolver` (`server/localization/screens.ts`) picks the `?locale=` param, then the session locale, then falls back to the default when that locale has no definitions. On the client, a `LocaleProvider` (`src/i18n/`) loads `/api/session` once, applies the same resolver, sets `document.documentElement.lang` to the resolved locale code (`en_US` / `ja_JP`, as the locked spec asserts), and gives pages a `useScreen()` hook. The shell chrome and the Language pages read their strings from it. The client reuses the server's resolver module and does not write a second one.
- **L6 Language page.** `/locale` is the page, `src/pages/locale.tsx`. `/localization` keeps rendering the same component so the locked site-shell cases and existing links keep working. `PRIMARY_AREAS` points at `/locale`. The page loads `/api/locales` through `useLoad`. The empty and error frames stay as they are. A native `<select>` labelled "Language" defaults to the current locale and offers the four fixed choices with their native names. "Change language" posts to `/api/locale`. On success the confirmation view shows the previous locale and `[data-testid="session-locale"]` with the new one. On failure an alert says it was unable to change the language. The header gets a language control linking to `/locale`, and the footer gets a "Change language" link.
- **L7 Catalog text.** `createDetailsStore()` is in-memory and keyed by `(entity, id, locale)`, and rejects a duplicate key. `createLocalizedCatalog({ store })` returns only rows whose locale equals the requested code, never substitutes another locale, and rejects a null or undefined locale. The persistent catalog tables are catalog browsing's (SWHR8-I-0004). They must keep the same `(id, locale)` key and no-fallback rule (promoted to ARCHITECTURE.md Key Decisions).
- **L8 Encoding.** Requests are read as UTF-8 (`readFormField` decodes the raw body with `TextDecoder("utf-8")` before parsing), and responses carry `charset=utf-8`. **4.3 is decided: support both.** SJIS uses `TextDecoder("shift_jis")`. JIS (ISO-2022-JP) uses a small converter: it walks the escape sequences, maps each JIS X 0208 byte pair to its Shift_JIS pair arithmetically, and then decodes as SJIS. This avoids a new dependency for the encoding Bun cannot decode.
- **L9 Formatting.** `formatCurrency(amount, locale, fractionDigits)` and `formatNumber` use `Intl.NumberFormat` with the BCP-47 form of the code (`en_US` becomes `en-US`). The currency comes from the locale: USD for en_US, JPY for ja_JP, CNY for zh_CN. `minimumFractionDigits` and `maximumFractionDigits` are set to the caller's value, so `1234.5, en_US, 2` gives `$1,234.50`. Keyword parsing (legacy `parseKeywords`) splits on whitespace and returns `[]` for empty input. It never returns null.
- **L10 Mail language.** `produceOrderMail({ order, stylesheets })` picks `stylesheets[notificationLocale(order.locale)]` and rejects when none exists. There is no English fallback. The default template map has en_US, ja_JP and zh_CN entries. Sending the e-mail is customer notifications' job (SWHR8-I-0009). Storing the locale on the order is order checkout's (SWHR8-I-0007).
- **L11 Preferred language.** Customer account (SWHR8-I-0005) does not exist yet. This change delivers the integration point: saving a profile calls `sessions.changeLocale(sessionId, preferredLanguage, now)`, which is the same path as the Language page. This is proven by a unit test of that call. The browser case SWHR8-C-0018 needs sign-on and `/account`, so it is deferred to SWHR8-I-0005.

## Spec discrepancies

Recorded here and on SWHR8-T-0008. The delta spec is unchanged.

- **S1 Mockup vs locked test, choice control.** The approved Language selection mockups (SWHR8-MCK-15/16) draw radio cards and a "choose one of the options" error. The locked spec SWHR8-C-0022/0023/0024 drives a `<select>` labelled "Language" with exactly four options and no placeholder. The select is built because the locked test is binding. The mockup's layout, copy, "Current language" panel and "Good to know" notes are followed around it.
- **S2 Locale list.** Legacy `web.xml` deployed `locales=en_US` only (legacy notes, line 1). The spec (SWHR8-R-0188) and brief say all three. The spec is followed. The admin guide's English and Japanese only list is the conflict the proposal already names.
- **S3 de_DE.** It is offered on the selection screen but has no screens. It is accepted as a session locale and falls back to en_US screens (SWHR8-R-0077.02), as the mockup's "no German screens yet" note says.
- **S4 Variant loss.** Legacy `getLocaleFromString` silently dropped variants (`en_US_x` gave a null country). The spec does not require reproducing that, so a three-part code is unparseable (L2).
- **S5 Null locale.** SWHR8-R-0072.03 specifies a failure only because legacy threw an NPE. It is implemented as an explicit rejection, which is still a failure with no data.
- **S6 Browser cases that need later capabilities.** SWHR8-C-0019 and SWHR8-C-0020 assert a `/catalog` page with heading "Catalog"/"カタログ", which catalog browsing (SWHR8-I-0004) builds. SWHR8-C-0018 needs `POST /api/signon` and the `/account` profile form, which customer account (SWHR8-I-0005) builds. All three are deferred to those briefs. The behaviour they cover (default en_US, Japanese screens, preferred language switch) is still implemented and unit-tested here through L4, L5 and L11.
- **S7 Acceptance browser specs are never collected.** `playwright.acceptance.config.ts` matches `**/e2e/**/*.spec.ts`, but `localization.spec.ts` sits directly in `tests/acceptance/localization/`. Already filed as defect SWHR8-T-0003, which is outside this sprint. The FEATURE carries its own project e2e spec for the Language page so the behaviour is exercised in CI regardless.
- **S8 Legacy dead paths.** Legacy `convertJISEncoding` and `parseKeywords` returned null on error and had no caller. Null returns are not reproduced (L8, L9).
