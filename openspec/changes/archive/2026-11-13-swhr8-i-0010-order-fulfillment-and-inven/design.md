# Design notes: legacy implementation of order fulfillment

## User interface

No `kind: screen` records were extracted for this capability; its user interface is unspecified. The inventory update is described only as behaviour (`order-fulfillment-REQ-0002`, `ORDER-FULFILLMENT-WORKFLOW-0007`, `ORDER-FULFILLMENT-BUSINESS-RULE-0008/0009`). Screen count: 0.

## How the legacy system implements it

- Supplier application: a message-driven bean reads the supplier purchase-order queue and calls `OrderFulfillmentFacadeEJB` (container transactions). `processAnOrder` skips lines where quantity equals quantity shipped; `checkInventory` compares inventory to the line quantity and swallows the not-found exception for unstocked items.
- Invoices are published as text messages on the order center invoice topic (`jms/opc/InvoiceTopic`), new connection per message.
- The inventory update page is protected by the administrator role with form login (no transport encryption). One transaction sets quantities, re-attempts PENDING orders and publishes invoices.
- Order center (`apps/opc`): on invoice receipt, shipped quantities are added per item; status becomes COMPLETED or SHIPPED_PART; only COMPLETED triggers the completed-order mail message.
- Components: `supplierpo` (CMP entity SupplierOrder, ContactInfo, LineItem with cascade delete), `purchaseorder`, `lineitem`, `processmanager` (one status record per order, pluggable transition delegates), `xmldocuments` (DTD-based documents, UTF-8, indentation), `servicelocator` (web variant caches resources; EJB variant does not; environment entries never cached).
- Schema (`petstore_oracle.sql`): `supplier_order` (po_status free text, no CHECK in the exported DDL), `supplier_line_item` (composite key, no FK to item), `inventory` (key item_id), named counters. The db pass records a PENDING/COMPLETED-only constraint; the DDL exports do not show it. Treat as disputed until the DDL is rechecked.

## Known issues and ambiguities

- Key collisions: the IR passes reuse some record keys for different behaviour in different modules (for example `ORDER-FULFILLMENT-BR-0002`, `-BR-0003`, `-BR-0004`, `-ENTITY-0001`, `ORDF-BR-0003`, `ORDF-ENT-0001`, `ORDF-INT-0001`, `ORDER-FULFILLMENT-BUSINESS-RULE-0001/0002/0003`, `ORDER-FULFILLMENT-REQUIREMENT-0001`, `ORDER-FULFILLMENT-WORKFLOW-0001`, `ORDER-FULFILLMENT-INTEGRATION-0001`). The spec states one variant per key; the recommendations file flags them for splitting. For the approved keys `ORDER-FULFILLMENT-BUSINESS-RULE-0002/0003` the supplier-application variant is used; the supplier purchase-order status/cascade-delete variants (status progression, cascade delete) are covered by `ORDER-FULFILLMENT-BR-0003/0004`. `ORDF-ENT-0001/0002` use the DDL (supplier order and line) variant; the purchase-order and process-status variants share the key.
- Order statuses differ by module: supplier order PENDING/COMPLETED (db), purchase order PENDING/APPROVED/DENIED/COMPLETED, order center COMPLETED/SHIPPED_PART. Transitions are constants only and not enforced in code.
- Suspected defect: `SupplierOrderEJB.getData` builds shipping info from an empty new object and omits status.
- Two XML validation notes disagree in places (structural check versus schema/catalog validation); see `ORDER-FULFILLMENT-BUSINESS-RULE-0001` and `ORDFUL-REQ-0008`.

## Codebase findings (planning, SWHR8-S-0009)

Read on the sprint branch before planning. The extracted notes above describe the legacy system; this section describes what this repository already has.

- **Approved decisions are already published, with no consumer.** The approval drain (`server/approval/queue.ts`) writes each applied decision as an OrderApproval document on `order-decision`, and the same transaction fans out to `order-status-mail`. Nothing drains `order-decision` yet: it is reserved for fulfilment (order-notifications design N7).
- **The outbox and drain pattern exist.** `queue_message` plus `databaseQueue(name, tx)`, `sendMessage` and the synchronous re-entrant drain in `server/approval/queue.ts`, copied by `server/notifications/queue.ts`. A new queue is a new `queue` name, never a new table (ARCHITECTURE.md Key Decisions).
- **Customer e-mail already accepts `shipped` and `completed`.** The `order-status-mail` drain parses `<OrderEvent><OrderId/><Event/></OrderEvent>` (`server/notifications/queue.ts`); `ORDER_EVENTS` and `orderEventDocument` live in `server/notifications/order-mail.ts`.
- **Order rows exist and have a shipped column.** `purchase_order`, `order_contact`, `order_credit_card`, `order_line_item` (with `quantity_shipped`, CHECK `<= quantity`) and `order_status` are in `db/schema.ts`. All order access goes through `server/checkout/repository.ts` (`getPurchaseOrder`, `statusRecords`). No delete or cascade exists for orders. Order ids are numeric strings from the `"1001"` counter in `id_counter` (`server/checkout/identifiers.ts`).
- **Status vocabulary exists.** `STATUSES` and `isRecognisedStatus` in `server/approval/service.ts` already hold PENDING, APPROVED, DENIED, SHIPPED_PART, COMPLETED.
- **`inventory` exists with the wrong shape for the locked tests.** `db/schema.ts` defines `inventory(item_id PK → item.id, qty NOT NULL)` with Drizzle property `qty` and no CHECK. It is written by `db/catalog-seed.ts` (sample data and `POST /api/test/seed`) and read by `server/jobs/catalog-check.ts` (via `scripts/`). The locked storage test inserts `{ itemId, quantity }`, expects `quantity: -1` to be rejected, and inserts item ids (`DUP-1`, `L-1`, `POS-1`) that are not catalog items.
- **There is no administrator concept.** Sign-on (`server/customer/auth.ts`) checks `signon_user` (plain-text passwords, seeded `j2ee` and `shopper`). There is no role, no `/admin` route, no admin page and no Logout control. The admin-order-management locked tests (SWHR8-I-0011, a later sprint) assume `/admin` shows a login form.
- **Navigation is one data list.** `src/constants/primary-areas.ts` drives the header nav, footer and landing page. The approved mockups show an "Administration" entry.
- **No XML serializer.** `server/checkout/xml.ts` has a small parser (`parseXml`) and the checkout's own document writer; nothing writes indented, typed XML.
- **Locked tests** (`tests/acceptance/order-fulfillment/`) fix the module boundary: `server/fulfillment/{service,documents,line-item,order-status,identifiers,process-manager,order-center,repository}.ts`, the `db/schema.ts` exports `contacts`, `supplierOrders`, `supplierLineItems` and `inventory.quantity`, and the UI contract `/admin/login` → `/admin/inventory` (`inventory-admin.spec.ts`). The pure service functions run over an in-memory `Store { inventory, supplierOrders, transaction }`.

## Planning decisions

- **F1. Pure core, adapters at the edge**, as in order approval and notifications. `server/fulfillment/service.ts`, `order-center.ts`, `documents.ts`, `line-item.ts`, `order-status.ts`, `identifiers.ts` and `process-manager.ts` export exactly the signatures in the header comments of the locked tests and take every collaborator (store, publish, queue, notify, now) as an argument. Production wiring lives in `server/fulfillment/queue.ts` (drains) and `server/fulfillment/store.ts` (database `Store`).
- **F2. Database `Store` = load, mutate, save inside one SQLite transaction.** `store.ts` builds a `Store` whose `transaction(fn)` opens a Drizzle transaction, loads the inventory rows and the PENDING supplier orders it needs into the plain objects the core mutates, runs `fn`, then writes back changed inventory quantities, line `shipped` values, statuses and new supplier orders. One drain row, or one inventory save, is one transaction (R-0151, R-0116).
- **F3. Message flow, one queue per consumer** (order-notifications N7):
  1. `order-decision` drain (new, in `server/fulfillment/queue.ts`): an APPROVED decision loads the order through `getPurchaseOrder` and calls `sendSupplierPurchaseOrder` with a queue that writes the supplier purchase-order document on `supplier-purchase-order`. A DENIED decision is marked delivered and does nothing. The transition runs through `deliverMessage` with a registry of one delegate (R-0211).
  2. `supplier-purchase-order` drain: `receivePurchaseOrder` stores the PENDING supplier order and attempts fulfilment at once. Each invoice is published on `invoice` in the same transaction.
  3. `invoice` drain (order center): `receiveInvoice` adds shipped quantities to `order_line_item.quantity_shipped`, sets `order_status` to SHIPPED_PART or COMPLETED, and fans out on `order-status-mail`: `shipped` for every invoice, plus `completed` only when the order completed (R-0017).
  The legacy "invoice topic" has one subscriber here, so it is a queue (`invoice`). `publishInvoices` keeps its connection-per-message contract (R-0117): in production the connection factory returns a `databaseQueue("invoice", tx)` writer whose `close` is a no-op. Each drain is the re-entrant synchronous pattern of `server/approval/queue.ts`, scheduled on the next tick after an enqueue and once on server start.
- **F4. Supplier tables are separate from order tables.** New tables in `db/schema.ts`: `contacts` (supplier contact: first/last name, email, phone, address fields; SQL name `supplier_contact`), `supplierOrders` (`supplier_order`: integer id PK = numeric order id, `order_date` timestamp, `status` CHECK in ('PENDING','COMPLETED'), `contact_id` NOT NULL FK), `supplierLineItems` (`supplier_line_item`: `supplier_order_id` NOT NULL FK, `line_number`, `category`, `product`, `item`, `quantity`, `unit_price` NOT NULL, `shipped` default 0; PK (order, line)). No FK from supplier lines to `item` (legacy DDL). Migration via `db:generate`, committed.
- **F5. `inventory` keeps one table, gains the fulfilment shape.** The Drizzle property is renamed `qty` → `quantity` (SQL column may stay `qty` to keep the migration a table rebuild only), a CHECK `quantity >= 0` is added, and the FK to `item` is dropped, because supplier stock is keyed by item id without a catalog FK in the legacy (`inventory` key `item_id`) and the locked tests insert non-catalog ids. `db/catalog-seed.ts`, `routes/api/test/seed.post.ts` and `server/jobs/catalog-check.ts` callers are updated to the new property only; their request/response shapes do not change. Catalog check C5 still compares item ids.
- **F6. Purchase-order cascade is a checkout-repository function.** R-0113 (`deletePurchaseOrder` cascading to contact, card and line items) and the `createPurchaseOrderWithDependents` / `findPurchaseOrderDependents` helpers named by the locked test are exported from `server/fulfillment/repository.ts` but implemented by delegating to new functions in `server/checkout/repository.ts`, which stays the only module touching order tables. Deletion runs in one transaction: line items, status, purchase order, then its contacts and card.
- **F7. Administrator role and form login.** New table `user_role(user_name → signon_user, role)`; the role name is `administrator`. The customer seed adds `jps_admin`/`admin` with the administrator role and `customer`/`customer-password` with none (the locked spec signs in as `customer`). New `server/admin/auth.ts`: `adminSignOn`, `adminSignOff`, `requireAdministrator(event)` (401 when not signed in to admin, 403 when signed in without the role). Admin sign-on state is a field on the existing session (one session, one cookie), reported additively by `GET /api/session` as `admin: { userName, isAdministrator } | null`. Routes: `POST /api/admin/signon`, `POST /api/admin/signoff`, `GET /api/admin/inventory`, `POST /api/admin/inventory`. Admin-order-management (SWHR8-I-0011) reuses this module and the `/admin/login` page.
- **F8. Inventory update screen.** `/admin/inventory` (page `src/pages/admin/inventory.tsx`) lists every inventory row with item description (from the catalog module, en_US text) and on-hand quantity, one "New quantity" input per row, "Clear entries" and "Save quantities". The server ignores blank, negative and non-integer entries (R-0009, brief "non-negative integer quantities"); the page also flags them inline as the mockup does. Saving calls `updateInventory` through the database `Store`, so stock is set and every PENDING supplier order is re-attempted in one transaction, and invoices go on `invoice`. A non-administrator sees the access-refused frame; a signed-out visitor is sent to `/admin/login?next=/admin/inventory`. Loading/error states use `src/components/shell`.
- **F9. Navigation.** One new `PRIMARY_AREAS` entry, "Administration", `href: "/admin/inventory"`. Admin-order-management repoints it to `/admin` when it ships its launcher.
- **F10. Documents.** `documents.ts` writes XML with `<?xml version="1.0" encoding="UTF-8"?>`, two-space indentation, a `<!DOCTYPE>` for SupplierOrder/Invoice and `xmlns` naming the supplier order namespace when `adapter: true`. Dates are `yyyy-MM-dd`. `validateDocument(xml, type)` checks the root element and required child elements in code; there is no DTD/XSD engine (as in order-approval SD6). Messages on the outbox carry these XML documents.
- **F11. Resource lookup (R-0153, R-0154) is a small module, `server/fulfillment/resources.ts`.** `createResourceLookup({ resolve, cache })` returns named resources (the drains' queues, the `now` clock), wraps a resolve failure in one `ResourceLookupError`, caches resolved resources when `cache` is on (web-tier variant) and never caches configuration entries (`process.env` reads). There is no JNDI; this keeps the requirement testable without inventing infrastructure.
- **F12. Date defaulting.** `readIncomingOrder` replaces a missing, malformed or future order date with `now` (locked C-0205 treats "tomorrow" as invalid).

## Phases

1. **Data model (tasks 1.x).** Schema (F4, F5, F7 `user_role`), migration, seed changes, repository (F6), identifiers.
2. **Supplier order intake (2.x).** `documents.ts` readers, `createSupplierPurchaseOrder`, `createSupplierOrder`, `receivePurchaseOrder`, the `supplier-purchase-order` drain.
3. **Fulfilment and invoicing (3.x).** `fulfillSupplierOrder`, invoice building, `publishInvoices`, `updateInventory`, database `Store`.
4. **Inventory update (4.x).** Admin auth, admin API routes, `/admin/login` and `/admin/inventory` pages, nav entry.
5. **Order center completion (5.x).** `order-center.ts`, the `order-decision` and `invoice` drains, fan-out to `order-status-mail`.
6. **Documents and messaging (6.x).** Serializers, validation, queue names.
7. **Resource lookup (7.x).** `resources.ts`, `process-manager.ts`.
8. **Test harness.** The locked suites in `tests/acceptance/order-fulfillment/` pass (Vitest and the Playwright `inventory-admin.spec.ts`). Unit tests under `src/test/server/fulfillment/` cover the database `Store` round-trip, the three drains end to end against the in-memory db (approved order → supplier order → invoice → COMPLETED and a `completed` row on `order-status-mail`; partial stock → SHIPPED_PART; stock save ships the waiting order), R-0118 (no locked case), R-0153/R-0154 (no locked cases), and the admin routes' 401/403. UI tests for the two admin pages. One Playwright spec in `e2e/` for the admin sign-in → inventory save happy path. The catalog-browsing, inventory-reporting catalog-check, order-approval, order-checkout and order-notifications suites stay green after the `inventory` change.
9. **CI.** No workflow change: the existing workflow runs doc-links, typecheck, lint, unit, build, E2E and acceptance on `vortex/**` pushes and pull requests.

## Spec discrepancies

Recorded at planning. The delta spec is left as extracted.

- **SD1. Supplier statuses vs order statuses.** R-0150 limits supplier orders to PENDING/COMPLETED (legacy DDL showed free text, see Known issues). Planned as a CHECK (F4); the locked C-0212 inserts only those two. Partly shipped is visible only on the order (`SHIPPED_PART`), never on the supplier order.
- **SD2. `inventory` shape.** The locked test and R-0102/R-0150 need `quantity` with CHECK `>= 0` and non-catalog item ids; the repo has `qty`, no CHECK, and an FK to `item` (catalog design C2 created it for fulfilment to extend). Resolved by F5.
- **SD3. Purchase-order cascade (R-0113) has no home in the current order model**, which has no delete. The locked test uses numeric ids and its own field names. Resolved by F6 inside the checkout repository.
- **SD4. Login form labels and controls differ between the mockups and the locked E2E spec.** Mockup SWHR8-MCK-53 labels the field "User name" and MCK-51 names the control "Sign out"; C-0229 locates `getByLabel("Username")` and a `/log ?out/i` link or button. MCK-55's heading "You don't have access to inventory update" matches none of `/access denied|forbidden|not authorized/i`, and MCK-55 shows no logout control while C-0229 requires one on the refused page. Resolved for the build: the field label reads "Username", the control reads "Log out" and appears on every admin page including the refused one, and the refused frame carries an "Access denied" line above the mockup heading. Everything else follows the mockups.
- **SD5. Demo accounts.** C-0229 signs in as `customer`/`customer-password`; the store seeds `j2ee` and `shopper`, and MCK-55 names `j2ee`. Both kinds are kept: `customer` is added (F7).
- **SD6. "Invoice topic" vs one consumer.** The legacy publishes invoices on a JMS topic. Here the only subscriber is the order center, so it is a queue (F3); a future subscriber gets its own queue by fan-out.
- **SD7. Resource lookup and transition delegates (R-0153, R-0154, R-0211) describe J2EE service-locator plumbing.** There is no JNDI or EJB tier; F11 and the process manager satisfy them with small injectable modules. R-0153 and R-0154 have no approved test case.
- **SD8. Requirement count.** `proposal.md` says 74 requirements; the delta spec carries 47 (after key de-duplication). Tasks are tagged against those 47.
- **SD9. Mockup file names.** The 40-character slug rule gives MCK-53 and MCK-54 the same name. MCK-54 is exported with a `-mobile` suffix; see `artifacts/SWHR8-S-0009/design/MANIFEST.md`.
