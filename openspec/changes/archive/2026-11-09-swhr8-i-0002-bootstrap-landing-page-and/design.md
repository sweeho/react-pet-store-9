# Design — Bootstrap, landing page and shared site shell

## Context

This change is generated by the platform for every migration and greenfield initiative (architecture doc 41). The capability brief canvas, its wireframes and its mockups are the detailed design; this document records the decisions every other capability relies on.

## Decisions

- **One shell.** Every page renders inside the same layout, header, navigation and footer. A capability adds content to the shell; it never draws its own chrome.
- **One navigation.** The global navigation lists every primary area and always links back to the landing page. A capability that adds a primary area adds one entry here rather than a second menu.
- **Shared states.** Empty, error and loading frames are components of the shell, reused by every page.
- **Existing boilerplate wins.** Where the repository already has an application scaffold, extend it rather than scaffold again.
- **Sign-in only if the product has it.** The shell carries a sign-in frame only when the product requirements call for authentication.

## Implementation decisions

- **Layout route.** `src/pages/_layout.tsx` default-exports `SiteLayout`. `vite.config.ts` adds `**/_layout.tsx` to `Pages({ exclude })` so it is not routed as `/_layout`. `src/main.tsx` mounts it once as the parent route: `useRoutes([{ element: <SiteLayout />, children: routes }])`. The catch-all "page not found" therefore renders inside the shell too.
- **Primary areas are data.** `src/constants/primary-areas.ts` exports `PRIMARY_AREAS: readonly PrimaryArea[]` (`{ slug, label, href, description }`). The navigation and the landing page both render from it, so a later capability adds one entry here and nowhere else. This sprint ships one entry: `{ slug: "localization", label: "Language", href: "/localization" }`. The label follows the mockup and the slug follows the proposal.
- **Shell landmarks.** `<header>` (banner) holds the store name "Pet Store", which links to `/`. `<nav aria-label="Global">` comes first in DOM order, with a "Home" link to `/` plus one link per area, and collapses into a headlessui `Dialog` menu below `lg`. `<main>` holds the `<Outlet />`. `<footer>` (contentinfo) repeats the area links. This follows `mockup-site-shell*.html`.
- **Shared frames** live in `src/components/shell/`: `EmptyFrame`, `ErrorFrame` (`onRetry` prop, "Try again" button) and `LoadingFrame` (`role="status"`), exported from `src/components/shell/index.ts`. They follow `mockup-empty-state*.html` and `mockup-error-state*.html`. `RootErrorBoundary` and the `Suspense` fallback in `main.tsx` reuse them.
- **Load helper.** `src/hooks/use-load.ts` exports `useLoad<T>(load: () => Promise<T>)`, which returns `{ status: "loading" | "ready" | "error", data, retry }`. Pages pick the frame from `status` and treat an empty array as "nothing to show".
- **Localization area entry page.** `src/pages/localization/index.tsx` is the area's landing screen. It fetches `GET /api/locales` through `useLoad` and renders `LoadingFrame`, `ErrorFrame`, `EmptyFrame` or a list of available languages. `routes/api/locales.ts` returns the supported locale codes as a JSON array (`[{ "code": "en_US" }]`, the deployed legacy value). The Localization capability (SWHR8-I-0003) later replaces the source and adds its `/locale` selection flow. This page exists because the nav must lead somewhere real and the locked frame tests (C-0139, C-0140) exercise it.
- **Out of scope.** Template demo pages (`about.tsx`, `users/*`) are not removed. They render inside the shell automatically. Sign-in is not added: the "Sign-in only if the product has it" decision defers it to customer-account.

## Spec discrepancies

Recorded at planning (SWHR8-T-0001). None of these edits the delta spec.

- **D1 Navigation entries.** The proposal and this design name one primary area (Localization). The approved mockups draw seven nav entries (Home, Catalog, Search, Cart, Account, Language, Administration). Resolution: ship Home plus the areas that exist (Language → `/localization`). Other entries are added to `PRIMARY_AREAS` as their capabilities ship, per "One navigation". Linking to unbuilt areas would put dead links on every page.
- **D2 Label vs slug.** The proposal says "Localization (`localization`)". The mockup labels the entry "Language", and the Localization change's own screens live at `/locale`. Resolution: label "Language", href `/localization` (the area entry page). The Localization capability decides whether `/localization` later redirects to `/locale`.
- **D3 Frame tests depend on another capability's page.** C-0139 and C-0140 import `@/pages/localization`, a page no requirement of this change names. Resolution: this change builds the thin area entry page (above) rather than deferring the cases, because the navigation needs the route anyway.
- **D4 Acceptance e2e spec never runs.** `playwright.acceptance.config.ts` matches only `**/e2e/**/*.spec.ts`, but `tests/acceptance/site-shell/landing-and-navigation.spec.ts` (and every other capability's spec) sits outside an `e2e/` directory. C-0136 and C-0137 therefore never execute in CI. Raised as DEFECT SWHR8-T-0003 (backlog, not this sprint). The FEATURE verifies the spec by running it directly.
- **D5 `tailwind.config.ts` exists** at the repo root although AGENTS.md and ARCHITECTURE.md state Tailwind is CSS-first with no config file. This change does not touch it. It is recorded for follow-up.
